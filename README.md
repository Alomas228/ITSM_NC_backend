# ITSM NC Backend

Серверная часть ITSM NC на ASP.NET Core (.NET 10). Для работы с PostgreSQL используются EF Core и Npgsql.

## Запуск

1. Открыть `ItsmNc.Api.slnx` в Visual Studio.
2. Выбрать профиль запуска `https`.
3. Запустить проект.

## Проверка

При запуске из Visual Studio открывается Swagger UI:

`https://localhost:7178/swagger`

1. Открыть Swagger в обычном Edge или Chrome по HTTPS-адресу выше.
2. Нажать **Authorize** и найти раздел **Keycloak (OAuth2, authorizationCode with PKCE)**.
3. Оставить client_id = student-service, поле client_secret пустым и выбранные scopes openid/profile/email.
4. Нажать **Authorize** в разделе Keycloak. Если окно не открылось, разрешить всплывающие окна для localhost. Встроенный браузер может не поддерживать этот сценарий.
5. В открывшемся окне Keycloak ввести тестовые логин и пароль. Пароль передаётся только провайдеру.
6. После возврата закрыть окно авторизации Swagger, раскрыть `GET /api/auth/me` и нажать **Try it out → Execute**.

У desk-admin есть student-service:user: ожидается 200 с данными пользователя. У alice нет роли нашего клиента: ожидается 403. Без входа ожидается 401. В поле client_secret ничего вводить не нужно.

Для смены пользователя нажать **Logout** в разделе Keycloak внутри Swagger, затем снова **Authorize** и войти другой учётной записью. Новый вход запрашивает пароль через prompt=login. **Logout** в Swagger удаляет только локальную авторизацию, а не завершает SSO-сессию Keycloak и не отзывает токен. После истечения 5 минут пройти вход повторно; автоматическое обновление в Swagger не реализовано.

Вариант **Bearer** оставлен для ручной вставки готового access token без префикса Bearer. Для обычного показа использовать только Keycloak; перед сменой способа удалить предыдущую авторизацию. Авторизация не сохраняется после перезагрузки страницы. Результат запроса находится в **Server response**; примеры ответов не являются результатом входа.

Для Swagger зарегистрирован callback `https://localhost:7178/swagger/oauth2-redirect.html` и origin `https://localhost:7178`. Использовать профиль запуска **https**. Другой порт или HTTP-адрес требуют отдельной регистрации в Keycloak.

Swagger UI и документ OpenAPI доступны только в Development. Исходный документ: `https://localhost:7178/openapi/v1.json`.

Запрос также можно отправить из файла `ItsmNc.Api.http` в Visual Studio.

## JWT-авторизация

API принимает access token, выданный Keycloak. Настройки находятся в разделе Keycloak файла appsettings.json:

- Authority — адрес realm.
- Audience — получатель токена: student-service.
- ClientId — клиент, из которого берутся роли: student-service.

Проверяются подпись RS256 через публичные ключи Keycloak, issuer, audience и срок действия. ID token для запросов к API не подходит. В токене должен быть audience student-service; одного значения azp недостаточно.

Для проверки текущего пользователя:

```powershell
Invoke-RestMethod "https://localhost:7178/api/auth/me" -Headers @{
    Authorization = "Bearer $env:KEYCLOAK_ACCESS_TOKEN"
}
```

Рабочий access token задаётся в переменной окружения текущего терминала. Его нельзя сохранять в исходниках или отправлять на сторонние сайты для разбора. Вход через реальный Keycloak, обновление и выход проверены. Настройки и результаты: [KEYCLOAK_AUTH.md](docs/integrations/KEYCLOAK_AUTH.md).

GET /api/auth/me возвращает subject, userName, roles и teamSlug. Роли берутся только из resource_access.student-service.roles. Доступ разрешён при любой непустой роли этого клиента. Роли service-desk и realm-роли сами по себе доступа не дают.

- 200 — токен действителен и есть роль нашего клиента.
- 401 — токен отсутствует, недействителен, просрочен или выдан не для этого API.
- 403 — токен действителен, но роли student-service нет.

teamSlug — значение из Keycloak; оно пока не заменяет TenantId и проверку изоляции собственных данных.

Срок access token задаёт Keycloak. API проверяет exp с техническим допуском часов 30 секунд. Обновление токена и завершение входа выполняются у провайдера. На стенде access token действует 300 секунд. После выхода refresh отклоняется, но уже выданный access token сохраняет доступ до истечения срока с учётом допуска часов.

## Тесты

```powershell
dotnet test ItsmNc.Api.Tests/ItsmNc.Api.Tests.csproj
```

В тестах настоящий JWT middleware проверяет подпись и метаданные через тестовый источник OIDC/JWKS. Приватные RSA-ключи создаются в памяти. Рабочие пароли и токены стенда не используются. Эти проверки не заменяют полный вход через настоящий Keycloak.


## Настройка базы данных

В Visual Studio нажать правой кнопкой по проекту `ItsmNc.Api` и открыть управление секретами пользователя. В `secrets.json` добавить строку подключения со своими данными:

```json
{
  "ConnectionStrings": {
    "AuthDatabase": "Host=localhost;Port=5432;Database=<имя_базы>;Username=<пользователь>;Password=<пароль>"
  }
}
```

Без этой настройки приложение запускается, но работать с базой данных не сможет. Это настройка существующей заготовки, а не выбор хранилища паролей или cookie-сессий для новой интеграционной архитектуры.

## Текущее состояние

Подключены EF Core, Npgsql и ASP.NET Core Identity. Добавлены модель пользователя и связи пользователей с ролями на уровне модели EF Core. Это заготовка по прежнему плану собственных учётных записей. Миграции и локальные операции с учётными записями не реализованы; эта заготовка не является источником входа через Keycloak.

По решению, зафиксированному 17 ноября 2026 года, собственный Backend интегрируется с готовым Keycloak (аутентификация, пользователи и роли) и Service Desk (заявки, статусы, REST API и webhooks). Отдельный Frontend команды использует Vue.js + TypeScript; здесь разрабатывается только Backend. Интеграции моделируют недоступный контур Artsofte и используются также при внедрении.

API проверяет JWT access token Keycloak. Базовый доступ разрешён всем ролям клиента student-service. Собственные пароли и MFA по старому плану не развиваются; существующая заготовка Identity требует отдельного пересмотра и не используется для нового входа. Вход с реальными тестовыми учётными записями, обновление токенов и выход проверены. Обязательный MFA и соответствие политик требованиям пока не обеспечены; браузерный сценарий отдельного frontend ещё не проверен. Интеграция заявок Service Desk пока не реализована.

Исходное ТЗ и рабочая документация хранятся отдельно. Пароли, ключи и другие секреты в репозиторий не добавляются.

## Роли

Названия ролей исходного ТЗ заданы в ApplicationRoles.cs. Их соответствие ролям Keycloak ещё не согласовано; таблица не доказывает разграничение доступа:

| Код | Роль |
| --- | --- |
| TenantAdministrator | Администратор тенантов, только SaaS |
| Administrator | Администратор |
| SupportEngineer | Инженер ТП |
| Supervisor | Руководитель |
| PortalUser | Пользователь портала |

Руководитель назначается из инженеров ТП по исходному ТЗ. Отображение этих ролей на роли Keycloak и права конкретных бизнес-действий ещё не определены.
